# Целостность и восстановление

## Что гарантирует транзакция

Балансы, денежные депозиты, комиссии, состояние писем, лотов, торговли и чеков изменяются внутри одной транзакции. Long/BigInteger исключают двоичные ошибки округления. Таблица operations хранит уникальный ID и параметры операции. Повтор не производит второй эффект; попытка использовать ID с другими параметрами отклоняется. Конкурирующие действия сериализуются единственным writer; при занятом хранилище вызывающий получает отказ и может повторить действие.

Сумма player + bank + guild + escrow + fees сохраняется для переводов/торговли/продаж. Административные изменения, стартовые балансы, API-награды, обмен валют, проценты, MINT, mob-rewards и death-loss имеют явно записанную причину создания/уничтожения. Комиссии учитываются на служебном `$fees`, а не исчезают из учёта. Чеки сохраняют деньги в `$voucher:<id>` до погашения.

SQLite использует WAL, synchronous=FULL и эксклюзивный файловый lease для экземпляра плагина. MariaDB использует InnoDB и GET_LOCK на схему. Это не распределённая экономика на несколько серверов: второй экземпляр отклоняется. Изменять таблицы вручную при работающем плагине нельзя из-за кэша балансов.

## Почему БД и инвентарь не атомарны

Paper-инвентарь и файл playerdata не участвуют в JDBC-транзакции. Поэтому перенос предмета — последовательность с журналом и запретом автоматического повтора неоднозначных этапов:

Внесение:
1. На потоке Paper клонировать стопку, проверить ограничения и получить полный byte[].
2. В фоне сохранить assets=IN_PREPARED, байты, владельца и журнал. До commit инвентарь не изменяется.
3. На потоке Paper проверить, что игрок онлайн, жив и предмет в исходной ячейке точно совпадает. При несовпадении поставить ABORTED.
4. Удалить предмет и вызвать player.saveData().
5. В фоне подтвердить READY. Только теперь показывать успешное сохранение.

Получение:
1. В фоне перевести READY → OUT_PREPARED; повторный получатель не получит ту же запись.
2. На потоке Paper найти свободную ячейку. При отсутствии места/игрока вернуть READY без выдачи.
3. Восстановить полные данные Paper, поместить предмет, вызвать saveData().
4. В фоне подтвердить CLAIMED. Не отправлять успех раньше commit.

На короткое время переноса блокируются действия с инвентарём, выбрасывание, подбирание, взаимодействие, смена рук и урон. Между этапами меняются только неизменяемые данные; Bukkit-объекты не передаются в фоновые задачи. Торговля/почта/аукцион перемещают уже сохранённые предметы внутри БД, поэтому им не требуется атомарность с двумя живыми инвентарями одновременно.

После перезапуска IN_PREPARED/OUT_PREPARED становятся QUARANTINE_IN/QUARANTINE_OUT. Блокируется следующий перенос этого владельца. Плагин **не пытается угадать**, сохранил ли Paper предмет непосредственно перед аварией. Это сохраняет доказательства и исключает автоматическую повторную выдачу, но требует решения администратора и может временно удерживать предмет.

Граница гарантий: saveData() — доступный API Paper, не двухфазный commit и не обещание физического fsync файлов мира. Падение питания, ошибки внешнего плагина, который напрямую меняет инвентарь, откат playerdata отдельно от БД и копирование миров могут нарушить согласованность. Не заявляется защита от всех дюпов. При внешнем откате восстановите согласованную резервную копию и проведите сверку журнала.

## Диагностика предметов

В консоли:

```
twm economy diagnose
twm economy recovery
```

После неоднозначной ошибки остановите сервер, сделайте копию текущих данных, затем запустите и посмотрите quarantine. Сопоставьте assets.data, item_journal, инвентарь игрока в актуальном playerdata и время события. Нельзя выбирать «database» только по имени/lore: сравнивайте полный предмет и его количество.

- Если предмет должен находиться **в БД** (его нет у игрока либо излишняя копия удалена под контролем администратора): `twm economy recovery <id> database` переводит запись в READY/INBOX.
- Если предмет уже **в инвентаре** и повторная выдача не нужна: `twm economy recovery <id> inventory` переводит запись в ABORTED, сохраняя байты/журнал для аудита.

Обе команды доступны только консоли, только для quarantine, и пишут ручное решение в журнал. Не удаляйте строки с данными спорного предмета. PREPARED во время работающего процесса не разрешается вручную: сначала штатный перезапуск переводит его в quarantine.

Для XP: `twm economy xp-recovery`. В журнале есть before_points, after_points, amount и направление. `applied` означает, что изменение игрока фактически сохранено; `not-applied` — не сохранено. Команда `twm economy xp-recovery <id> applied/not-applied` соответственно завершает либо возвращает резерв. Опыт MMOCore не используется при этой сверке.

Открытая торговля при перезапуске отменяется: деньги возвращаются отдельными письмами (так лимит кошелька не ломает возврат), предметы — в INBOX. Незавершённый аукцион сохраняется; истёкшие лоты возвращаются в почту. COD оплата и письмо выручки фиксируются в одной транзакции.

## Резервные копии

`twm economy backup` выполняется в рабочей очереди: для SQLite — консистентный VACUUM INTO; для MariaDB — SQL dump своей схемы. Сообщение «Операция сохранена» появляется после завершения. Имя backup-* выводится отдельно. Это копия **только экономики**, а не playerdata и всего сервера.

Для полноценной точки восстановления:

1. Запретить вход и остановить сервер через stop; дождаться завершения процесса.
2. Скопировать **всю папку server** в новую дату. Не копировать только economy.sqlite из работающего WAL без правильного backup: часть данных может находиться в `-wal`.
3. Проверить архив и SHA-256. Хранить несколько версий и отдельную копию вне диска сервера.
4. Восстанавливать мир/playerdata, БД и конфигурацию из одной точки. Текущую папку перед восстановлением отложить отдельно, не удалять.
5. Запустить единственный экземпляр, выполнить diagnose, recovery и сверку нескольких предметов/балансов.

SQLite backup можно открыть командой Python `sqlite3.connect(...).execute('PRAGMA integrity_check')`. SQL dump MariaDB восстанавливается **в новую пустую схему** соответствующим клиентом; сначала проверьте на отдельном сервере. MySQL/MariaDB драйвер не переносит SQLite автоматически. `storage.identity` блокирует случайную смену backend или адреса. Перенос между backend требует отдельного проверенного экспорта, сверки всех таблиц и осознанного обновления marker; такой конвертер не входит в эту версию.

Миграции внутренней схемы автоматические, текущая версия 3. БД с более новой версией отвергается. После изменения формата данных не откатывайте старый JAR без согласованного восстановления копии. Изменение precision существующей валюты и удаление валюты с остатками запрещены.
